# ADR-0006：草稿可编辑，发布修订不可变，运行时只读已发布修订

- **状态**：已接受
- **日期**：2026-09-21
- **关联**：系统设计草案 §6.2、§6.3、§6.7、§7、§11

## 上下文

`RuleModelRevisionId` 的主要作用是**形成不可变快照边界**：变量、规则、赋值、绑定和测试用例都属于同一修订。草稿修改不会触碰当前发布修订，回滚也只是重新激活历史修订（系统设计 §6.3）。

`RuleModel` 通过 `ActiveRevisionId` 指向当前运行修订，`Status` 取 `Active` / `Archived`，并持有顶层 `ConcurrencyStamp`（系统设计 §6.2）。

`RuleModelRevision` 自身带 `Status`（`Draft` / `Published` / `Abandoned`）、`BasedOnRevisionId`、`RevisionNo`、`ContentHash`、`ConcurrencyStamp`、`ChangeSummary`（系统设计 §6.3）。

`ReleaseRecord` 记录激活修订、前一修订、发布序号、发布或回滚类型、内容哈希、校验摘要、操作人和时间，是**发布审计，不是可再次编辑的规则内容**（系统设计 §6.7）。

§7 进一步规定：已发布 Revision 及其子实体不可修改，也不可通过产品功能删除。

技术验收标准要求「发布修订不可变，发布切换具有事务一致性和乐观并发保护」（系统设计 §11）。

> **待补**：
> - 一次修订的数据量级是多少（变量数、规则数、绑定数的典型值）？这决定「每个修订一份完整快照」是否可承受。
> - 回滚后 `ActiveRevisionId` 指回旧修订，但 `RevisionNo` 是递增的——界面上怎么让用户看出「现在跑的是第 3 版，虽然已经发到第 7 版了」？
> - 并发控制有两层（`RuleModel` 顶层、`Revision` 草稿层），什么操作会同时碰到两层？

## 决策

草稿可编辑，发布修订不可变，运行时只读取已发布修订。

## 考虑过的替代方案

> **待补**：是否评估过以下方向，以及为什么没选：
> - **就地编辑 + 独立历史表**：只维护一份当前版本，变更前把旧值写进历史表；
> - **事件溯源**：以变更事件为权威，当前状态由重放得出；
> - **单版本 + 变更日志**：不做快照，靠日志回溯。

## 后果

- 变量、规则、赋值、绑定、测试用例全部挂在 `RevisionId` 上，数据量随修订数量线性增长。
- 回滚是「重新激活历史修订」，不是「把内容改回去」，因此不会产生新的内容版本，但会产生新的 `ReleaseRecord`。
- 需要保留期清理机制处理 `Abandoned` 草稿（与 ADR-0009 相关）。
- 内容一致性靠 `ContentHash` 保证，可用于检测发布后的意外改动。

> **待补**：修订快照的保留策略——是否所有历史修订都永久保留，还是达到某个数量后归档。
