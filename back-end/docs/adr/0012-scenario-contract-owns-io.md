# ADR-0012：场景契约拥有入口和必需出口

- **状态**：已接受
- **日期**：2026-09-21
- **关联**：产品设计草案 §6.3；系统设计草案 §5.2、§6.4；ODS 垂直接入设计 §4

## 上下文

入口和出口既服务于规则编制，也构成接入 App 与 NRuleEngine 的运行契约。若业务用户可以任意修改入口或新增出口，宿主可能无法提供输入或识别输出；若所有变量都由代码固定，又无法满足规则内部逐步计算的需要。

## 决策

场景代码契约定义入口变量和必需出口变量的编码、方向与类型。创建规则模型修订时，将它们实例化为契约变量，并由 NRuleEngine 为逻辑变量生成或继承 `StableKey`；规则维护 API 不允许修改这些契约属性。

首版不为 `VariableDefinition` 增加 `ContractVariableKey`。契约变量使用 `Origin=Contract + Code` 与当前 `ContractVersion` 中的 `VariableContract.Code` 对齐，规则内部引用仍统一使用 `StableKey`。契约变量的 `Code` 是代码契约的一部分，修改编码必须通过新的契约版本完成。

首版允许规则维护者新增、修改和删除中间变量，不允许新增场景契约之外的入口或出口。规则维护者可以维护契约允许覆盖的展示信息、默认值、单位和精度。

## 考虑过的替代方案

- 所有入口、中间和出口都由用户自由维护：最灵活，但无法保证宿主调用契约稳定。
- 所有变量都由代码注册：契约最稳定，但每次增加内部计算变量都需要开发和部署。
- 允许用户新增可选出口：需要宿主具备动态输出消费机制，首版 ODS 场景没有该需求。

## 后果

- ODS 可以在编译和启动阶段明确知道必须提供哪些输入、必须消费哪些输出。
- 中间变量仍可由业务规则维护者自由编制，不需要修改 ODS 代码。
- 场景契约升级需要定义变量新增、删除和类型变更的兼容规则。
- `VariableDefinition` 需要区分 `Origin=Contract/UserDefined`；`Origin` 只决定维护边界，变量身份仍由 `StableKey` 承担。
- 不增加 `ContractVariableKey`，避免 `StableKey`、`Code` 和契约键形成三套身份；代价是契约变量重编码必须作为契约版本变更处理。
