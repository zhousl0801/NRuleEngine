# ADR-0019：独立条件集与明确候选判定

- **状态**：已接受
- **日期**：2026-09-29
- **关联**：ADR-0006、ADR-0015、ADR-0016；[条件集设计与使用](../architecture/ConditionSet-条件集设计与使用.md)

## 上下文

已有业务场景中的机组参数资格和设计规则条件只返回“是否命中”；参数与属性值由 ODS 保存，并通过旧规则标识关联。现有 `RuleModel` 要求必需输出与规则赋值，把空赋值规则放进去会改变其领域语义。

## 决策

新增独立的 `ConditionSet` / `ConditionSetRevision`，注册只有输入的条件场景。修订保存布尔 AST、输入快照、精确契约版本和优先级；发布后不可修改。调用方明确指定候选编码，按 `AllMatches` 或 `FirstMatch` 判定。正常无命中与输入/求值错误分开；最高优先级并列命中在 `FirstMatch` 下报歧义。引擎返回稳定编码和发布修订，不保存 ODS 业务属性值。

## 考虑过的替代方案

- 在 `RuleModel` 中创建没有赋值的规则：现有发布校验与运行成功语义依赖必需出口，改动会模糊赋值型规则的不变量。
- 把 ODS 参数或 MIC 属性伪装为输出变量：属性结构、单位、舍入及生命周期归 ODS 管理，复制进引擎会造成两份事实来源。
- 自动扫描场景全部条件集：候选范围由业务上下文决定，全局扫描容易命中无关配置，也增加运行成本。

## 后果

- ODS 需要维护旧 `RuleId` / `ConditionSetId` 到稳定条件集编码的映射，并在调用前确定候选范围。
- 发布要求正反样本，保存发布与回滚历史；宿主需为新 EF 表生成数据库迁移。
- 现有赋值型 `RuleModel` 的输出义务和执行接口保持原语义。实际生产迁移须先核对旧引擎排序、边界和批量结果。
