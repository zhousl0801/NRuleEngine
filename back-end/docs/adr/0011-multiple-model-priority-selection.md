# ADR-0011：同一场景多模型按绑定优先级唯一裁决

- **状态**：已接受
- **日期**：2026-09-21
- **关联**：产品设计草案 §6.5；系统设计草案 §6.6、§9.3

## 上下文

同一个 App 的同一业务场景可能需要多个规则模型分别承载不同业务资源、产品范围或维护边界。若限制为单一模型，所有规则会被迫集中到一个大型修订；若允许多个模型但没有统一裁决规则，运行时结果将不确定。

## 决策

同一个 `AppCode + ScenarioCode` 允许多个 RuleModel 同时拥有活动发布修订。运行时对所有命中绑定按 `Priority` 数值从高到低裁决：最高优先级唯一时执行其所属修订；最高优先级并列时返回 `AmbiguousBinding`，不得按创建时间或数据库顺序隐式选择。

`Priority` 的比较范围是整个 `AppCode + ScenarioCode`。发布校验应阻止可判定的同优先级重叠绑定，运行时保留最终歧义保护。

## 考虑过的替代方案

- 每个场景只允许一个活动模型：实现简单，但模型会持续膨胀，难以按业务资源拆分维护。
- 多模型按创建时间或模型编码兜底：结果虽然确定，但业务含义隐蔽，不适合作为规则裁决语义。
- 使用“条件更具体者优先”：需要定义跨类型维度的通用具体度算法，首版复杂度过高。

## 后果

- 可以按产品范围、工艺或资源拆分模型，同时维持确定性执行。
- 发布校验必须跨 RuleModel 查询同一 App 和场景的活动绑定。
- 并发发布两个潜在冲突模型时，需要数据库事务或锁保证不会同时越过歧义校验。
- 无匹配返回 `NoMatchingBinding`；是否兜底由宿主显式处理。
