# ADR-0008：首版不实现变量敏感标记与自动脱敏

- **状态**：已废弃为 ADR（保留为产品首版延期项）
- **日期**：2026-09-21
- **关联**：产品设计草案 §3 非目标；系统设计草案 §1 第 8 条

## 上下文

文档中与本决策相关的表述只有一句：首版不实现变量级敏感标记和自动脱敏（产品设计 §3 非目标，系统设计 §1 第 8 条）。

除此之外，**产品设计草案和系统设计草案都没有展开**：哪些变量可能承载敏感数据、谁需要看脱敏后的结果、不脱敏的风险由谁承担。

> **待补**（这几项决定这条决策是「合理延期」还是「隐性风险」）：
> - 当前预期接入的场景（尺寸展开、机组参数计算）里，变量会不会带客户信息、合同号、价格之类的数据？
> - 执行 Trace 会保存变量取值（产品设计 §6.6），这些 Trace 谁可以看？保存多久？
> - 如果接入方自己有脱敏要求，靠什么机制满足——宿主在 Provider 层处理，还是组件要提供钩子？

## 决策

首版不实现变量级敏感标记和自动脱敏。

## 考虑过的替代方案

**变量级敏感标记 + 自动脱敏。** 即在 `VariableDefinition` 上增加敏感标记，由组件在 Trace、试算结果和审计输出中自动脱敏。文档将其列为非目标，即**延期而非否决**。

> **待补**：延期到什么时候？触发条件是什么（例如「首个带敏感数据的场景接入时」）？没有触发条件的延期容易变成永久不做。

## 后果

- 组件不需要处理脱敏逻辑，`VariableDefinition` 结构保持简单。
- 敏感数据的保护责任完全落在宿主和接入方，组件不提供任何机制。
- 后续若要加上，会改动 `VariableDefinition`（加字段）、Trace 输出路径和试算结果的序列化——**属于破坏性变更**，成本高于首版就留出位置。

## 这条是否该是 ADR

本决策**没有取舍**，只有一个延期判断，因此与其他 ADR 性质不同。两个处理方式：

- **保留为 ADR**：如果上面的「待补」问完发现有真实风险，那它就是一条需要记录的决策，应补上完整的上下文与后果。
- **退回产品文档**：如果只是「首版不做」，放回产品设计草案的「非目标」一节更合适，不必单独成篇。

建议先回答「待补」的三个问题，再决定去留。

## 后续处理

2026-09-21 评审后确认：变量敏感标记仍不进入首版，但这只是范围裁剪，不作为独立架构决策。本文件为保留历史不删除；有效范围以产品设计草案的“首版延期项”为准。
