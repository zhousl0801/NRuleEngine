# ADR-0007：表达式使用结构化 AST，变量以稳定标识引用

- **状态**：已接受（`StableKey` 形式由 ADR-0017 确定）
- **日期**：2026-09-21
- **关联**：系统设计草案 §6.4、§8、§11、§12 第 3 条

## 上下文

`VariableDefinition` 同时持有 `StableKey`（不可变逻辑标识）和 `Code`（可读别名，可重命名），稳定标识的语义在系统设计 §6.4 中定义为五条：

- AST 引用 `StableKey`，不引用名称字符串；
- 从修订 3 创建修订 4 时，同一个逻辑变量保持相同 `StableKey`；
- 改名只改变 `Code` 或 `Name`，引用不变；
- 删除后再创建一个同名变量必须生成新的 `StableKey`，避免误接旧引用；
- 数据库可使用 `RevisionId + StableKey` 建立复合唯一约束和引用完整性。

表达式模型分三层（系统设计 §8）：源文本用于编辑和展示，**AST 是执行和引用分析的权威结构**，`ExpressionReference` 是由编译器生成的查询投影，用于影响分析和依赖图。类型检查在保存时局部执行、在发布时对完整修订执行。Sequential 模式下赋值写回执行上下文，依赖图必须无环。

技术验收标准要求「变量改名后 AST 引用保持有效；删除再新建不会复用旧身份」（系统设计 §11）。

> **待补**：
> - 第 4 条「删除后新建同名变量必须生成新 StableKey」在界面上会不会让用户困惑（看起来同名却接不上）？有没有提示机制？
> - `ExpressionReference` 投影是每次保存重算，还是增量维护？修订数量增长后影响分析的性能如何？

## 决策

表达式使用结构化 AST 和稳定标识引用变量，不以显示名称字符串关联。

## 考虑过的替代方案

> **待补**：是否评估过以下方向，以及为什么没选：
> - **字符串表达式 + 按名称关联**：实现最简单，但改名即断引用；
> - **以 `Code` 作为引用键**：比 `Name` 稳定，但仍随重命名失效；
> - **只存源文本、不存 AST**：省一层序列化，但每次执行都要重新解析，且无法做静态引用分析；
> - **在数据库保存「仓储类型名 + 方法名」再反射调用**：系统设计 §5.5 已对绑定维度明确排除了这条路，表达式侧是否同理？

## 后果

- 改名安全，影响分析和依赖图可以做在编译期而不是运行期。
- 需要维护 `StableKey` 的生成规则、跨修订复制规则，以及 `ExpressionReference` 投影的一致性。
- **AST 的序列化格式成为兼容性负担**：新增操作符或类型时，必须能读取既有 AST。
- 禁止反射、文件、网络、数据库访问和任意代码执行（系统设计 §8），表达式能力边界由此固定。

## 形式决定记录

`StableKey` 形式已由 [ADR-0017](0017-first-version-expression-scope.md) 定为 Guid。原候选方案如下：

| 选项 | 可读性 | 备注 |
|---|---|---|
| Guid | 无 | 生成简单，占 16 字节 |
| ULID | 无（但有序） | 可排序，便于调试 |
| 可读字符串 | 高 | 需解决重名与冲突，且可能被误当成 `Code` |
