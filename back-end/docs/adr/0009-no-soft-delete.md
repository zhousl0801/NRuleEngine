# ADR-0009：不采用软删除

- **状态**：已接受
- **日期**：2026-09-21
- **关联**：系统设计草案 §7、§6.2、§6.3、§11

## 上下文

系统设计 §7 完整规定了删除、归档与历史策略，共六条：

- 不采用软删除，实体不实现 `ISoftDelete`；
- `RuleModel` 使用 `Archived` 表达停止继续使用，归档不会移除历史发布和执行所需数据；
- 已发布 Revision 及其子实体不可修改，也不可通过产品功能删除；
- 草稿中的变量、规则和赋值可以物理删除，删除前必须执行引用检查；
- 不再使用的草稿标记为 `Abandoned`，由明确的保留期清理任务物理删除；
- App 或场景代码注册失效时，目录投影标记为 `Unavailable`，以保护历史发布的可解释性；
- 物理清理必须遵守外键限制，不得级联删除仍被发布记录或执行记录引用的数据。

文档给出的理由是：**历史能力由不可变发布修订、ReleaseRecord 和审计字段提供，而不是依赖软删除。**

产品设计 §7.3 从交互侧补充：删除前先返回直接和间接引用，有阻塞引用时不执行删除并提供跳转入口。

> **待补**：
> - 保留期具体多长？由谁配置（组件常量、宿主配置，还是接入应用自己跑清理任务）？
> - 物理删除草稿后，如果该草稿曾参与过试算或校验，这些记录怎么处理？
> - ABP 的审计日志默认也会记录删除，与这里的物理删除策略如何配合？

## 决策

不采用软删除，使用状态、不可变修订和明确的物理删除策略。

## 考虑过的替代方案

**`ISoftDelete` 软删除。** 这是 ABP 的默认能力，实现成本低（实体实现接口即可，ABP 自动加过滤）。本决策不采用，理由见下。

> **待补**：是否评估过以下方向，以及为什么没选：
> - 软删除 + 定期物理清理（两段式）；
> - 只归档不删除（草稿也永久保留，靠状态过滤）；
> - 软删除只用在 `RuleModel` 上，子实体物理删。

## 后果

- 查询不需要到处带 `IsDeleted` 过滤，唯一约束也不用为软删除做特殊处理（例如 `AppCode + Code` 的唯一性不会因为软删除行而冲突）。
- **删除是不可逆的**，误删草稿无法从数据库恢复，只能靠备份。
- 需要额外的保留期清理任务，并保证它遵守外键约束、不碰已发布数据。
- 历史可解释性由「不可变发布修订 + ReleaseRecord + 审计字段」三者共同承担，任何一处缺失都会削弱它。

> **待补**：清理任务的运行方式与失败处理（谁跑、多久跑一次、失败告警给谁）。
