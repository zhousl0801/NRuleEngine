# ADR-0001：全新设计，不继承旧 RuleEngine

- **状态**：已接受
- **日期**：2026-09-21
- **关联**：产品设计草案 §1 文档边界、§3 非目标；系统设计草案 §3 仓库结构

## 上下文

现有 RuleEngine 是既有组件，NRuleEngine 定位为从零设计的通用规则编制与运行组件，**不是现有 RuleEngine 的 V2**（产品设计 §1）。

产品设计草案已明确三项首阶段不承诺的事项（产品设计 §3）：不兼容旧 RuleEngine 的表结构和接口、不自动迁移旧规则数据、不把 NRuleEngine 独立部署成必须通过 HTTP 调用的平台。

系统设计草案的仓库结构中没有为兼容旧模型预留任何项目或适配层（系统设计 §3）。

> **待补**：
> - 旧 RuleEngine 具体卡在哪里？表结构耦合、扩展成本、维护成本，还是执行语义不够用？
> - 现有旧规则的数量级是多少？人工重建的工作量评估过吗？
> - 是否需要一段并存期（旧规则继续跑、新规则逐步替换）？

## 决策

NRuleEngine 是全新设计，不继承旧 RuleEngine 的表结构和命名。

## 考虑过的替代方案

文档中已被排除的方向：

- **演进旧 RuleEngine**——不兼容旧表结构和接口、不自动迁移旧数据（产品设计 §3）。
- **独立部署为 HTTP 平台**——明确排除（产品设计 §3）。

> **待补**：是否还评估过「在旧 RuleEngine 上加一层通用抽象」或「fork 后改造」？为什么放弃？

## 后果

- 旧规则需要人工重建，不存在自动迁移路径。
- 命名、表结构和领域模型不受旧组件约束，可按 ABP 惯例重新设计。
- 一段时间内两套规则引擎可能并存，需要明确各自的适用边界。

> **待补**：并存期的过渡策略（如果有）需要写清。
