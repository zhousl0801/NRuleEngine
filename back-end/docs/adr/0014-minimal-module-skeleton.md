# ADR-0014：首批建立最小 ABP 模块骨架

- **状态**：框架版本决策被 [ADR-0022](0022-net8-abp8-baseline.md) 取代；模块骨架决策保留
- **日期**：2026-09-23
- **关联**：ADR-0002、ADR-0004；系统设计草案 §3、§4、§11

## 上下文

ADR-0004 确定标准 ABP 分层。原草案同时规划了 11 个源码项目和 6 个测试项目，其中表达式、运行时、抽象层和 HttpApi.Client 的独立发布边界尚未确定。当前只有设计文档，尚无需要迁移的 NRuleEngine 实现。

## 决策

首批骨架最初集中放在 `Nrule-engine/` 子目录，公开仓库中归档在 `back-end/`，建立 `Domain.Shared`、`Domain`、`Application.Contracts`、`Application`、`EntityFrameworkCore`、`HttpApi` 六个标准模块。`.slnx` 显式设置 `/src/`、`/test/` 解决方案文件夹。测试采用 `TestBase`、`Domain.Tests`、`Application.Tests`、`EntityFrameworkCore.Tests` 分层，不使用控制台程序冒充测试项目；首批各层测试只验证 ABP 模块初始化，EF Core 数据库测试随映射实现补充。表达式和执行器先作为模块内部实现；出现清晰的复用、替换或独立发布需求时再拆成独立项目。HttpApi.Client 在确有远程调用方时再增加。

所有项目使用 `net10.0`。依赖版本统一放在 `Directory.Packages.props`，本次选用已核实兼容 .NET 10 的稳定 ABP 10.6.0。项目结构与依赖关系须在骨架阶段通过构建和模块装配验证。

## 考虑过的替代方案

- 一次创建原草案的 17 个项目：目录完整，但多数项目初期为空，会提前形成不必要的公开包和依赖边界。
- 把全部代码放进单个项目：起步快，但偏离已确定的 ABP 模块集成方式，不利于宿主按层引用。

## 后果

- ADR-0004 的“采用标准 ABP 分层”结论保持有效；其上下文中的 17 个项目数量由本 ADR 调整。
- 首批骨架不包含实体、API、表达式编译器或业务场景实现，不能用“构建和模块测试通过”代替产品能力验收。
- 当表达式或运行时需要单独对外发布时，必须另行定义公开契约、版本兼容和依赖方向，再拆项目。
- 分层测试项目是本地测试入口，不是生产 Host；原先的 `Modularity.Smoke` 控制台项目已移出解决方案。
