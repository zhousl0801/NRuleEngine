# ADR-0010：App 完全由接入应用代码注册

- **状态**：已接受
- **日期**：2026-09-21
- **关联**：系统设计草案 §2、§5.1、§5.2、§5.3、§6.1、§11

## 上下文

`App` 是一级接入边界，以 `AppCode` 作为稳定逻辑标识（例如 `ODS`）。系统设计 §2 定义了它**参与**什么：场景目录隔离、规则模型编码唯一约束、缓存键和运行时查询、审计与指标的数据查询范围、避免同一数据库中不同宿主应用的模型互相污染。

同一节也定义了它**不是**什么：不是 ABP `TenantId` 的替代品、不是物理部署边界、不是业务组织或工厂权限边界、不是供用户任意创建的文件夹。

注册本身是代码契约（系统设计 §2、§5.1）：

- 接入应用实现 `IRuleAppContributor` 注册 App；
- `AppCode` 一经发布不得修改，需要更换编码时按新 App 接入处理；
- 编制台只能读取 App 目录，不能创建、编辑或删除 App；
- 数据库可以保存可重建的只读目录投影，但**投影不是权威来源**；
- 场景注册必须引用一个已经注册的 `AppCode`，否则**宿主启动失败**。

场景侧同理：NRuleEngine 不扫描数据表猜测场景，也不允许用户创建没有运行时契约的场景，接入应用通过 `IRuleScenarioContributor` 在启动时注册（系统设计 §5.2）。启动时依次收集 App、校验场景的 `AppCode` 已注册、校验 `AppCode + ScenarioCode + ContractVersion` 唯一、构建内存目录、同步可选投影、把已不存在的场景版本标记为 `Unavailable`（系统设计 §5.3）。

`APP_CATALOG` 与 `SCENARIO_CATALOG` 是代码注册信息的可选只读投影，**删除投影后必须可以从注册代码完整重建**（系统设计 §6.1）。

技术验收标准要求「App 只能通过代码注册，管理 API 不提供 App 写入能力」「场景注册冲突在启动阶段给出明确错误」（系统设计 §11）。

> **待补**：
> - 启动失败是硬失败（宿主起不来）还是可降级？现在文档写的是「阻止启动」，但接入方配置错一个场景编码就让整个宿主起不来，代价是否可接受？
> - 如果部署中只有 ODS 一个接入方，`AppCode` 仍保留在接口和顶层聚合中（系统设计 §2）。这个「预留」在多久之后可以被重新审视？
> - 目录投影既然是可重建的，为什么还需要它——是为了查询性能，还是为了让数据库层也能做审计？

## 决策

App 完全由接入应用代码注册，不能通过数据库、管理 API 或编制台维护。

## 考虑过的替代方案

> **待补**：是否评估过以下方向，以及为什么没选：
> - **App 存数据库，由管理界面维护**：新增接入方无需改代码和重新部署，但 App 与代码契约可能脱节；
> - **混合模式**：代码注册为权威，数据库允许覆盖部分展示属性（名称、说明、排序）；
> - **配置文件注册**：介于代码与数据库之间，但同样存在与代码契约脱节的风险。

## 后果

- **新增或修改接入方必须改代码并重新部署宿主**，无法运维期热加。
- 配置错误（App 冲突、空编码、场景引用未注册 App）在**启动阶段**暴露，而不是运行到某个场景才失败——这是本决策的主要收益。
- 数据库只保存可重建的只读投影，投影损坏或丢失不影响权威来源，但也意味着**投影中的数据不可信**，任何以投影为准的逻辑都是错的。
- `AppCode` 一经发布不可修改，等价于给接入边界加了一次性命名约束。

> **待补**：投影与实际注册代码不一致时（例如投影同步失败），运行时以哪边为准、如何告警。
