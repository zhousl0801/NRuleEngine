# 架构决策记录（ADR）

本目录记录 NRuleEngine 的架构决策。每条决策单独成篇，保留**当时**的上下文、考虑过的替代方案和后果。

系统设计草案 [§1 架构决策索引](../architecture/NRuleEngine-系统设计草案.md) 只保留索引表，不重复正文。

## 为什么要单独成篇

原来 10 条决策挤在系统设计草案的一节里，每条只有一句结论。**结论是对的，但"为什么"没有地方放**——为什么不选另一个方案、这个选择换来了什么代价、以后什么情况下需要重新审视。

ADR 就是给"为什么"腾出的位置。

## 格式

每条 ADR 固定五段：

| 段 | 写什么 |
|---|---|
| **状态** | 已接受 / 提议中 / 已废弃 / 被 ADR-XXXX 取代 |
| **关联** | 相关文档章节与相邻 ADR |
| **上下文** | 做这个决策时的事实、约束、已有条件。**只写事实，不写理由** |
| **决策** | 一句话结论。与系统设计草案 §1 原文保持一致 |
| **考虑过的替代方案** | 还有哪些路可以走，为什么没走。**这一节最容易空，但它最值钱** |
| **后果** | 这个选择带来的结果，好的坏的都写。包含"以后可能要改回来"的地方 |

正文里出现 `> **待补**：` 的，是需要人工补充的内容。**不要用推测填空**——编出来的理由比空着更糟。

## 新增一条

1. 取下一个编号，文件名用 `NNNN-kebab-case-英文短名.md`（**ASCII 路径**，避免跨平台乱码）。
2. 复制现有 ADR 的结构。
3. 补进本文件索引表和系统设计草案 §1 的索引表。
4. 如果新决策**取代**了旧决策：新 ADR 的「关联」指向旧编号，旧 ADR 的状态改为「被 ADR-NNNN 取代」，**不要删除旧文件**。

## 与系统设计草案 §12 的关系

系统设计草案 §12「待形成 ADR 的问题」是**还没定的事**。定了之后：

- 从 §12 移除；
- 写成一条新 ADR（或并入已有 ADR 的「未决」一节，如 ADR-0007 的 `StableKey` 形式）。
